# Modelo de amenazas

**PROPUESTA:** análisis preliminar sin implementación, mediciones ni controles comprobados. Probabilidad e impacto cualitativos (alta/media/baja) son hipótesis dependientes del entorno; riesgo residual es lo que quedaría incluso si las medidas propuestas se implementan y verifican. Aprobación de controles y criterios de aceptación **PENDIENTE**.

## Activos, actores y fronteras

Activos: inventario y etiquetas de sitio, cuentas y sesiones de VulnTrack, resultados NVD/ZAP, integridad del historial, disponibilidad de API/NVD, lista y autorización de destinos, secretos operativos. Actores: operador de campo, analista web, persona autorizadora de destinos (función propuesta), atacante autenticado/no autenticado, servicios NVD, aplicaciones de prueba y operador de plataforma. La identidad y atribuciones exactas están **PENDIENTE**.

Fronteras: móvil o navegador → API; API → base de datos; API → NVD por HTTPS; API → ejecución aislada de ZAP → aplicación de prueba autorizada; procesos → registros/reportes. Entradas no confiables: campos, IDs, búsqueda CPE, respuestas externas, enlaces/redirecciones, DNS, solicitudes de escaneo, reportes y dependencias. Los datos del formulario nunca deben convertirse en órdenes, SQL o dirección de escaneo sin validación.

## Capas para ZAP y condición de bloqueo

1. **PROPUESTA:** autoridad humana registra un destino de prueba exacto, vigencia, esquema, nombre, puerto y redes permitidas; el cliente solo selecciona ID. La administración de esta lista no está diseñada ni aprobada.
2. **PROPUESTA:** revalidar permisos y vigencia en cola y ejecución, normalizar IDNA, puertos, IP literales y variantes; denegar acceso a redes de gestión, metadata, loopback, enlace local y terceros salvo que una red de laboratorio explícitamente autorizada cumpla la política aprobada. No prohibir toda red privada indiscriminadamente: el laboratorio puede ser privado.
3. **PROPUESTA:** imponer red de salida aislada por destino y puerto, controlar resolución y cambios de DNS en el punto de conexión, bloquear redirecciones fuera de alcance y probar tanto IPv4 como IPv6. Si proxy o firewall no puede verificar nombre y dirección reales por conexión, no usarlo como única barrera. Definir procedimiento de cambios de IP, TLS y comportamiento ante resolución múltiple antes de autorizar.
4. **PROPUESTA:** ejecutar Baseline sin Active Scan, configuración fija, límites de tiempo, procesos, memoria y respuestas; sin privilegios ni credenciales de clientes; recolectar solo resultados necesarios. Evitar `shell` y parámetros elegidos por cliente.
5. **PROPUESTA:** ensayar en laboratorio controlado: destino permitido, externo, redirect, DNS rebinding, IP literal, loopback, IPv6, puerto no autorizado y revocación. Registrar solo hechos necesarios. Hasta demostrar con pruebas que no hay conexiones fuera de alcance, la ejecución debe quedar bloqueada.

**PENDIENTE:** aprobar arquitectura efectiva de aislamiento, autorización humana, inventario de destinos, responsable de control, monitoreo, expiración de evidencias y criterios de riesgo aceptable. No se realizaron escaneos ni se verificó ningún control real.
